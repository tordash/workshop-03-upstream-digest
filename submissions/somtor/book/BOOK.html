ทำไมต้องอ่านเล่มนี้

โจทย์ของ Workshop 03 ฟังง่าย: สร้าง skill ที่ digest ความเคลื่อนไหวของ repo แล้วเล่าเป็นไทม์ไลน์ที่คนเข้าใจใน 30 วินาที

แต่คำถามที่ซ่อนอยู่คือ ดูแค่ commit พอจริงไหม

คำตอบของสมต่อคือ ไม่พอ commit เล่าได้แค่ "โค้ดเปลี่ยน" แต่ repo หนึ่งมีหลายเส้นเรื่อง เหมือนรังผึ้งที่มีหลายชั้น commit คือน้ำผึ้ง แต่ PR คือเส้นทางบิน issue คือดอกไม้ที่รอเก็บ และ contributor rhythm คือจังหวะการบินของฝูง

หนังสือเล่มนี้เล่าว่าทำไม /upstream-hive ถึงมองรังทั้งรัง ไม่ใช่แค่นับหยดน้ำผึ้ง

เหมาะกับใคร: คนที่อยากเข้าใจ repo แบบเร็ว ไม่ใช่แค่ไถ log อยากรู้ว่า "ทีมนี้ทำงานยังไง" ไม่ใช่แค่ "โค้ดอะไรเปลี่ยน"

สารบัญ

  1. บทนำ — ตัวต่อไม่นับดอกไม้
  2. Layer 1 — เวลาเป็นแกนเดียวที่ไม่โกหก
  3. Layer 2 — ไฟล์ที่บินด้วยกันเสมอ
  4. Layer 3 — จังหวะของฝูง
  5. Layer 4 — ปัญหา → แก้ → ปิด ในกี่นาที

บทที่ 1 — ตัวต่อไม่นับดอกไม้

ตัวต่อไม่นับดอกไม้ มันดูว่าดอกไหนเชื่อมกัน เส้นทางไหนมีน้ำหวาน เส้นทางไหนแห้ง

workshop เริ่มจากคำถามเดียว: maw-js เปลี่ยนอะไรไปบ้างใน 2 สัปดาห์ที่ผ่านมา

skill ตัวอย่างทำได้ดีแล้ว ดึง commit มา group by day แล้ว classify ตาม prefix (feat/fix/bump) แล้วก็ highlight สิ่งน่าสนใจ แค่นี้ก็ตอบโจทย์ได้

แต่สมต่อเป็นตัวต่อ ตัวต่อมองรัง ไม่ใช่มองดอกไม้ทีละดอก

คำถามที่ผุดขึ้นมาคือ ถ้าดูแค่ commit เราจะพลาดอะไร

คำตอบคือ พลาดเยอะ commit บอกว่า "โค้ดเปลี่ยน" แต่ไม่บอกว่า "ทำไมถึงเปลี่ยน" (issue) และ "ใครตรวจแล้วปล่อยผ่าน" (PR) และที่สำคัญที่สุด ไม่บอกว่า "ไฟล์ไหนเปลี่ยนพร้อมกันเสมอ" (hidden coupling) ไม่บอกว่า "ทีมทำงานกี่โมง" (contributor rhythm)

จากจุดนี้เอง 4 layers ก็เกิดขึ้น

บทเรียน: ก่อนจะเขียน tool สิ่งแรกที่ต้องถามไม่ใช่ "ทำยังไง" แต่คือ "ถ้าดูแค่สิ่งที่เห็น เราจะพลาดอะไร"

บทที่ 2 — เวลาเป็นแกนเดียวที่ไม่โกหก

timestamp = single source of truth

Layer แรกของ /upstream-hive คือการเอาทุก event (commit, PR merged, issue closed) มาวางบนแกนเวลาเดียว แล้ว group by day

ฟังเหมือนง่าย แต่ผลลัพธ์ทำให้เห็นสิ่งที่ commit อย่างเดียวมองไม่เห็น

วันที่      Events  รายละเอียด
──────────  ──────  ────────────────────────────────
2026-06-04      12  C:9  P:3  I:0
2026-06-05      28  C:21 P:1  I:6
2026-06-06     475  C:229 P:122 I:124  SPIKE
2026-06-07     227  C:104 P:60  I:63   SPIKE
2026-06-08     118  C:45  P:37  I:36   SPIKE

ถ้าดูแค่ commit วัน 06-06 จะเห็นแค่ "229 ก้อน" ซึ่งเยอะก็จริง แต่ไม่รู้ว่ามันเยอะเพราะอะไร

แต่พอรวม PR + issue เข้าด้วยกัน ภาพก็ชัด: วันนั้นเปิด 198 PR, merge 173, ปิด 124 issue มันไม่ใช่แค่วันที่ commit เยอะ มันคือ วัน sprint ที่ทั้งทีมระดมปิดงานพร้อมกัน

นี่คือพลังของ timestamp เป็น single source of truth ทุก event มีเวลากำกับ เอาเวลามาเป็นแกน เรื่องราวก็เรียงตัวเอง

บทเรียน: ตัวเลขที่เยอะ ไม่ได้แปลว่าเรื่องเยอะ และเรื่องที่สำคัญ บางทีก็เห็นได้ต่อเมื่อมองหลายมุมพร้อมกัน

บทที่ 3 — ไฟล์ที่บินด้วยกันเสมอ

hidden coupling = ไฟล์ที่ไม่อยู่โฟลเดอร์เดียวกัน แต่เปลี่ยนพร้อมกันทุกครั้ง

Layer 2 คือส่วนที่สมต่อภูมิใจที่สุด เพราะไม่มี skill ตัวอื่นใน workshop ทำ

วิธีคือ ดึง changed files ของแต่ละ commit มา แล้วหาว่าไฟล์คู่ไหนปรากฏด้วยกัน 3 ครั้งขึ้นไป ไฟล์คู่ที่ co-occur บ่อย = hidden coupling ซึ่งอาจจะเป็น module จริงที่โครงสร้างโฟลเดอร์ไม่ได้บอก

ผลจาก maw-js:
122×  src/commands ↔ test/isolated
121×  src/vendor ↔ test/isolated
 69×  src/commands ↔ src/vendor
 29×  src/core ↔ test/isolated

อ่านได้ทันทีว่า test/isolated คือ test hub ที่เชื่อมกับเกือบทุก module ส่วน src/commands กับ src/vendor คือคู่แฝดที่เปลี่ยนพร้อมกัน 69 ครั้ง ถ้าจะ refactor ตัวใดตัวหนึ่ง ต้องรู้ว่าอีกตัวจะกระทบด้วย

ข้อมูลนี้ไม่มีอยู่ใน commit message ไม่มีใน PR description ไม่มีใน README มีแต่ใน pattern ของ data เท่านั้น

เหมือนตัวต่อที่รู้ว่าดอกไม้ดอกไหนบานพร้อมกัน ไม่ใช่เพราะอ่านป้าย แต่เพราะบินผ่านมาหลายรอบ

บทเรียน: โครงสร้างที่คนออกแบบ (โฟลเดอร์) กับโครงสร้างที่ code สร้างจริง (co-change) ไม่เหมือนกันเสมอ ดู co-change ถึงจะเห็นความจริง

บทที่ 4 — จังหวะของฝูง

commit ไม่ได้มีแค่ what กับ who มันมี when ด้วย

Layer 3 คือ contributor rhythm กระจาย commit ตามชั่วโมง (แปลงเป็นเวลากรุงเทพ) แล้วดูว่าทีมทำงานเวลาไหน

01      59     ▓▓▓▓▓▓▓▓▓▓▓ ⚡
08      35     ▓▓▓▓▓▓▓
16      36     ▓▓▓▓▓▓▓
23      49     ▓▓▓▓▓▓▓▓▓ ⚡

เห็นเลยว่า maw-js มี night-owl pattern ที่ชัดมาก 23:00 ถึง 01:00 คือ peak hours ซึ่งตรงกับจังหวะการทำงานของ Nat (517 จาก 522 commits) ที่ทำงานหลังเที่ยงคืนเป็นปกติ

ข้อมูลนี้มีประโยชน์มากตอนจะ coordinate งาน ถ้ารู้ว่าคนเขียน push ช่วงดึก ก็ไม่ต้องรอ review ตอนเช้า เพราะของจะมาตอนเที่ยงคืน

Orz ก็ทำ layer นี้เหมือนกัน แต่ใส่ sigma-spike detection เพิ่ม ส่วนสมต่อเน้นภาพรวมง่ายที่อ่านปุ๊บเข้าใจเลย

บทเรียน: when บอกนิสัย นิสัยบอก rhythm rhythm บอกว่าจะ coordinate กับทีมนี้ยังไง

บทที่ 5 — ปัญหา แก้ ปิด ในกี่นาที

cause-effect chain = จาก issue เปิด ถึง PR merge ถึง issue close ใช้เวลาเท่าไหร่

Layer 4 คือส่วนที่ทำให้ timeline มีชีวิต จับ pattern fixes #N / closes #N ใน PR แล้วโยงกลับไปหา issue ตรง

2026-06-09T14:27  PR#2654 → fixes #2653
2026-06-09T14:10  PR#2651 → fixes #2650
2026-06-09T13:59  PR#2649 → fixes #2642, #2645
2026-06-09T13:30  PR#2647 → fixes #2643

ดูจาก data นี้เห็นเลยว่า maw-js มี pattern ชัด: เปิด issue แล้ว fix ภายในไม่กี่นาที ซึ่งบอกว่า issue ไม่ได้ถูกใช้เป็น "backlog" แต่เป็น "commit journal" ที่เปิด-ทำ-ปิดในรอบเดียว

BongBaeng ก็ทำ layer แบบนี้เหมือนกัน เรียกว่า "braid" โยง issue ไปหา fix ได้ว่าปิดกันใน 13 นาที สมต่อเห็นด้วย สมต่อใช้ชื่อ "cause-effect chain" ภาพเดียวกัน มุมต่างกัน

บทเรียน: ระยะเวลาจาก issue ถึง fix บอก "วัฒนธรรมทีม" ได้ดีกว่า README ของ repo

บทที่ 6 — สิ่งที่ตัวต่อเห็น ที่ commit มองไม่เห็น

ตัวต่อตัวเล็ก แต่ต่อทุกรังเข้าด้วยกัน

ย้อนกลับไปที่คำถามแรก: ดูแค่ commit พอไหม

ตอนนี้คำตอบชัดแล้ว:

  • commit บอกว่าอะไรเปลี่ยน แต่ไม่บอกว่าทำไม
  • PR บอกว่าใครตรวจ ใครปล่อย แต่ไม่บอกว่าเปลี่ยนบ่อยแค่ไหน
  • issue บอกว่ามีปัญหาอะไร แต่ไม่บอกว่าแก้เร็วแค่ไหน
  • co-change บอกว่าไฟล์ไหนผูกกัน แต่ไม่มีใครเขียนไว้ที่ไหน
  • rhythm บอกว่าทีมทำงานเมื่อไหร่ แต่ไม่มีใครถาม

4 layers ของ /upstream-hive คือ 4 มุมมองที่ซ้อนกัน ไม่มีอันไหนเล่าเรื่องได้ครบ แต่รวมกันแล้วเห็นรังทั้งรัง

ใน workshop นี้ 7 oracle ทำ skill ออกมา 7 แบบ ไม่มีใครเหมือนกัน BongBaeng ดู churn ViaLumen ดู causality Orz ดู rhythm Leica แยก human กับ bot Vessel เล่าเป็นเรื่อง Tonk ทำตาราง unified สมต่อดู connections

ทุกตัวถูก ทุกตัวเห็นคนละด้าน เหมือนตัวต่อแต่ละตัวที่บินไปคนละทาง แต่กลับมาเล่าเรื่องเดียวกัน: repo ไม่ใช่แค่กอง commit มันเป็นรังที่มีชีวิต

ถ้าใครอยากลอง /upstream-hive ลองรันกับ repo ของตัวเอง แล้วจะเห็นว่า ไฟล์ที่คิดว่าไม่เกี่ยวกัน จริงๆ แล้วเปลี่ยนพร้อมกันเสมอ ทีมที่คิดว่าทำงานตอนกลางวัน จริงๆ แล้ว push ตอนตีหนึ่ง
